# 보드게임 BM 선택적 통합안 v0.1

> **작업 ID**: `BM-001`, `BM-002`
> **작성**: `Codex` (2026-08-23)
> **상태**: PM 검토 대기 — v0.5 확정안이나 구현 지시가 아님
> **입력**: PM 제공 「메모리 반도체 경영 시뮬레이션 '실리콘 팹' 기획안 및 구조 설계」
> **영향 제한**: 이 문서는 `src/core.js`, `validate.js`, 승인된 P0 에셋 11종을 변경하지 않는다.

## 1. 결론

BM 결과는 **반영할 수 있다.** 다만 Brass·Kanban EV·Silicon Valley·Acquire의 규칙을 한 게임에
그대로 합치는 방식은 채택하지 않는다. 현재 제품의 핵심인 **30~40분, 분기당 최대 3개 결정, 장기
베팅의 사후 인과 이해**를 유지하면서 다음 세 가지 설계 원리만 우선 흡수하는 안을 권장한다.

1. 숫자 대시보드를 **부서가 구획된 개인 팹 보드**로 바꾼다.
2. 증설·노드 전환·HBM 퀄을 **앞/뒤가 있는 프로젝트 타일**로 표현하고, 완료 때 타일을 뒤집는다.
3. 타일이 뒤집힐 때 기존 `trace-schema-v0.1.md`를 사용한 **분기 결과 인과 카드**를 연다.

즉 첫 통합 대상은 새로운 경제 규칙이 아니라, 현재 규칙을 손으로 만지는 듯 이해하게 만드는
**상태 표현·기다림·완료 보상**이다.

## 2. 전체 결합을 권장하지 않는 이유

현재 제품과 BM 보고서는 제품 형태가 다르다.

| 기준 | 현재 v0.5 후보 | BM 보고서의 전체안 |
|---|---|---|
| 핵심 경험 | 불완전한 신호 아래 10년 장기 투자 | 네트워크·퍼즐·워커 배치·확률·M&A 복합전 |
| 플레이 구조 | 사람 1명 대 경쟁 AI, 40분기 | 다인 경쟁 보드게임 중심 |
| 플레이 시간 | 30~40분 | 원작들이 각각 대체로 60~120분급 |
| 행동 예산 | 분기당 변경 최대 3개 | 부서 시프트·카드·퍼즐·생산 추첨 등 다중 예산 |
| 결과 원칙 | 같은 시드+같은 결정=같은 결과, 사후 설명 가능 | 손기술·추첨·상대 배치가 결과에 큰 영향 |
| 구현 제약 | 외부 의존성 없는 단일 HTML | 글로벌 맵·다수 타일·물리 애니메이션 요구 |

공식 제품 안내도 Brass: Birmingham을 2~4인용 60~120분의 헤비급 경제 게임, Kanban EV를
90~120분 게임으로 소개한다. Silicon Valley 규칙서도 1~4인 60~120분과 라운드당 3개 행동을
전제로 한다. 각 게임의 핵심 시스템을 모두 넣으면 하나의 30~40분 캐주얼 루프가 아니라 여러 게임이
직렬로 연결된다.

BM 보고서 자체도 구현 사양으로 바로 쓰기에는 보완이 필요하다.

- 수율 로지스틱 함수가 붙여넣기 과정에서 누락되어 수치 모델을 재현할 수 없다.
- 참고문헌에 같은 출처가 반복되고 비공식 요약·공략이 섞여 있다.
- 수율 백, 리소그래피 퍼즐, HBM 리듬 게임이 동일 제품 품질에 중복 관여해 원인 귀속이 흐려진다.
- “완벽히 계승”보다 원작의 긴장을 분석하고 우리 고유의 규칙·표현으로 다시 설계해야 한다.

따라서 이 자료는 **재미 후보 라이브러리**로 사용하고, 밸런스 수치나 완성 규칙으로 간주하지 않는다.

## 3. 요소별 채택 판정

판정 기준은 (1) 장기 베팅 강화, (2) 인과 가시성, (3) 30~40분 적합성, (4) 구현 비용,
(5) 기존 코어와의 충돌이다.

| BM 요소 | 판정 | DRAM 게임용 변환 | 이유·게이트 |
|---|---|---|---|
| 산업 타일 뒤집기 | **우선 반영** | 프로젝트 완료 시 타일 앞면→결과면 전환 | 기다림의 보상과 상태 변화가 한눈에 보임. 새 규칙 불필요 |
| 부서별 보드 | **우선 반영** | R&D·Fab·Production·Packaging·Finance 화면 구획 | 기존 6개 레버를 공간적으로 이해시키되 워커 선점 규칙은 넣지 않음 |
| 제한된 행동력 | **이미 반영** | 분기당 최대 3개 결정 토큰 | D-003과 동일한 긴장. 별도 시프트 자원은 중복 |
| Develop·구세대 제거 | **표현만 반영** | 노드 전환을 구세대→신세대 프로젝트 타일로 표현 | 별도 폐기 행동을 넣으면 기술 러시가 자동 정답이 될 수 있어 밸런스 검증 전 보류 |
| Innovator·2nd Mover | **후속 실험** | 경쟁사보다 먼저/늦게 완료한 노드·HBM의 회고 배지 | 우선 점수 없는 피드백으로 검증. 보상 수치는 S2 기준선 뒤 검토 |
| 거시 이벤트 카드 | **표현만 반영** | 기존 시대·정권·구조 단절을 카드로 공개 | 새 랜덤 보정치를 매 분기 추가하지 않아 시장 진실 원천을 보존 |
| 16비트·물리적 보드 질감 | **아트 실험** | 프로젝트 타일·결정 토큰·카드에 한정 | 가독성·색각·저사양 검증 후 확장. 원작 아트나 UI를 복제하지 않음 |
| 수율 백·푸시 유어 럭 | **보류** | 현재는 수율 확률과 투자 효과를 토큰 구성으로 시각화하는 안만 연구 | 현 코어 수율은 결정론적이므로 추첨 연출을 붙이면 거짓 인과가 됨. 규칙화는 별도 A/B 필요 |
| 폴리오미노 R&D 퍼즐 | **보류** | 선택형 R&D 실험 모드 후보 | 공간 퍼즐 실력이 경영 전략을 덮을 위험. 모바일·접근성·턴 시간 검증 필요 |
| HBM 타이밍·리듬 게임 | **기본 루프 반려** | 완료 연출로만 사용 | 손기술이 HBM 수익을 결정하면 전략 결과의 사후 설명성과 접근성이 깨짐 |

## 4. 권장 첫 수직 슬라이스 — Fab Operations Board

새로운 맵이나 미니게임 대신, 현재 플레이 화면의 왼쪽·중앙 영역을 다음처럼 재구성한다.

```text
┌ 시장 신호 ─────────────────────────────────────────────┐
│ 국면 · 신뢰도 · 가격 추세 · 경쟁사 발표                          │
├ R&D ─────────┬ Fab ─────────┬ Production ───┬ Packaging ─┤
│ 노드 전환 타일  │ 증설 타일       │ 가동률·수율       │ HBM 퀄 타일     │
│ 예상 완료 T21  │ 예상 완료 T15  │ 현재 산출         │ 승인 조건       │
├─────────────────────────────────────────────────────────┤
│ Finance: 현금 · 분기 비용 · 결정 토큰 0/3                         │
└─────────────────────────────────────────────────────────┘
```

### 한 분기의 사용 흐름

1. 플레이어가 시장 신호와 진행 중 프로젝트를 본다.
2. 최대 3개의 결정 토큰을 관련 부서에 놓는다. 실제 저장값은 기존 6개 레버와 같다.
3. 분기 정산 후 프로젝트 타일의 남은 턴·위험 상태가 갱신된다.
4. 완료된 타일이 뒤집히며 실제 완료 턴과 즉시/지속 효과를 보여준다.
5. 같은 순간 인과 카드가 열려 결정·시장·경쟁사 기여를 분리해 설명한다.

예를 들어 T9에 시작한 노드 전환 타일은 12분기 동안 Fab 보드에 남는다. 완료 시 “양산 진입” 면으로
뒤집히지만, 동시에 “Ramp Valley: 정산 2회” 경고와 인과 카드가 열린다. 플레이어는 생산량 감소가
무작위 벌칙이 아니라 T9의 장기 베팅이 낳은 예정된 전환 비용임을 이해한다.

### 이 슬라이스가 흡수하는 BM 가치

- Brass의 **건설→대기→뒤집기→보상** 리듬.
- Kanban의 **부서 간 업무 흐름과 제한된 시간**.
- Silicon Valley의 **즉시 효과와 지속 효과 구분**.
- 픽셀 보드게임의 **물리적 촉감과 완료 타격감**.

하지만 네트워크 경로, 새 자원, 워커 선점, 손기술, M&A는 추가하지 않아 기존 코어와 검증 기준을
그대로 유지한다.

## 5. 프로토타입 성공 기준

`Fab Operations Board`는 예뻐 보이는지만 평가하지 않는다. 동일한 시드·결정을 기존 UI와 비교한다.

| 지표 | 통과 기준 |
|---|---|
| 인과 이해 | 결과 직후 10초 안에 원인 결정을 맞힌 참여자 80% 이상 |
| 프로젝트 상태 이해 | 남은 기간과 위험 상태를 맞힌 참여자 80% 이상 |
| 턴 속도 | 분기당 중앙값 60초 이하 |
| 결정 제약 | 3개 초과 제출 0건 |
| 코어 동일성 | 같은 시드·같은 결정의 정산 결과가 기존 UI와 완전히 동일 |
| 체감 | 5점 척도 “공장을 운영하는 느낌” 중앙값 4 이상 |

실패하면 규칙을 더 넣지 않고 보드 구획·타일 정보량·뒤집기 연출을 먼저 줄인다.

## 6. 실행 순서와 업무분장 제안

v0.5 문서 전체의 PM 승인 전에는 구현하지 않는다. 승인 이후에도 기존 S1~S4 순서를 건너뛰지 않는다.

| 단계 | 작업 | 주담당 | 리뷰·결정 | 상태 |
|---|---|---|---|---|
| BM0 | 이 문서에서 선택적 통합 방향 결정 | PM | Claude+Codex 의견 | PM 결정 대기 |
| 기존 게이트 | v0.5 승인 → S1~S3 결함·fixture·지표 → S4 인과 카드 | 기존 분장 유지 | 기존 규칙 | 대기 |
| BM1 | Fab Operations Board 저충실도 와이어프레임 A | Codex | PM+Claude | BM0 뒤 |
| BM2 | 동일 데이터 계약을 쓴 독립 시안 B | Claude | PM+Codex | BM0 뒤 |
| BM3 | 기존 UI/A/B 3안의 5인 이해도 테스트 | PM 실행, Codex 설계 | Claude 결과 검토 | BM1~2 뒤 |
| BM4 | 통과 시 프로젝트 타일·부서 보드만 제품안에 채택 | 채택 시 담당 지정 | PM 최종 결정 | BM3 뒤 |
| BM5 | Innovator 배지 등 **한 가지** 규칙만 추가 A/B | Claude 구현, Codex 감사 | PM | S2 기준선 뒤 |

### PM이 결정할 두 항목

1. `BM-001`: BM을 현재 1인 게임의 **표현·상태 레이어**로 선택 통합할지.
2. `BM-002`: 첫 슬라이스를 **Fab Operations Board + 프로젝트 타일 뒤집기**로 할지.

전체 네트워크·워커 플레이스먼트·M&A를 꼭 만들고 싶다면 현재 v0.5에 누적하지 않고,
`Silicon Fab Board`라는 별도 2~4인 모드/후속 프로젝트로 분리하는 편이 안전하다.
