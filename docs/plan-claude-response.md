## 2. 항목별 재현 결과

### P0-A. Ramp Valley — 2분기 설계, 실제 1분기

`src/core.js` `advancePhysical()`에서 카운터를 설정한 직후 같은 호출 안에서 감소시킨다.

```js
c.rampValleyQuartersRemaining = RAMP_VALLEY_QUARTERS;   // = 2  (line 154)
...
if (c.rampValleyQuartersRemaining > 0) c.rampValleyQuartersRemaining -= 1;  // 즉시 1로 (line 157)
```

전환 완료 턴(T12)에 2→1이 되고 그 턴에 페널티가 걸린다. 다음 턴에는 1→0이 되어 `computeProductivity`의
`rampMult` 조건(`> 0`)을 통과하지 못한다. 실측 40턴 추적:

```
T11 node=2 transitionLeft=1  valleyCounter=0  rampMult=1.00
T12 node=3 transitionLeft=-  valleyCounter=1  rampMult=0.80   <== 유일한 페널티 분기
T13 node=3 transitionLeft=-  valleyCounter=0  rampMult=1.00
→ 페널티 적용 분기 수: 1 (설계 요구: 2)
```

Codex의 D-002 처방("카운터 감소를 생산량 계산 이후로")에 동의한다.

### P0-B. 분기당 3개 결정 제한 — 코어 미강제

한 분기에 6개 레버를 전부 제출한 결과 **6개 전부 반영**됐다.
`applyPlayerDecisions()`에 개수 검사가 없고, 제한은 `src/ui.js`의 `actionCount()`에만 있다.

의미: `validate.js`의 5개 전략은 매 분기 실제 게임 규칙보다 많은 결정을 내릴 수 있으므로,
**지금까지의 밸런스 검증 결과는 실제 플레이 규칙을 대표하지 않는다.** Codex D-003에 동의한다.

### P0-C. HBM 퀄 — 준비 없이 익음

`computeMix()`는 노드 게이트만 보고 카운터를 올린다. HBM 배분 0%를 6분기 유지한 마이크론:

```
T1 hbmShareTarget=0.00 hbmQualQuarters=5  qualPassed=true  hbmBits=0.0
T6 hbmShareTarget=0.00 hbmQualQuarters=10 qualPassed=true  hbmBits=0.0
```

HBM을 한 웨이퍼도 안 돌렸는데 퀄이 통과 상태로 유지된다. 설계 문서 §4.2의
"컨벤셔널→HBM 전환은 퀄 게이트 때문에 훨씬 느리다"는 비대칭이 **완전히 무력화**돼 있다.
Codex D-006(HBM 준비 상태기계)에 동의한다.

### P0-D. CXMT 노드격차 KPI

`state.initialGap`은 게임 시작 시 **플레이어 진영 기준으로 한 번만** 계산되는데,
`finalScore(c, all, state.initialGap)`가 이 값을 전 진영에 그대로 넘긴다.

SKH로 플레이할 때: 리더 노드=2, SKH=2 → `initialGap = 0`. CXMT의 진짜 격차는 2인데도 0을 받고,
`gapClose = initialGap > 0 ? ... : 0` 때문에 CXMT의 격차축소 항이 **항상 0으로 강제**된다.
CXMT를 직접 플레이할 때만 우연히 맞는다. 확인.

## 3. 신규 발견 P0-E — `capacityPressure` 부호 반전 (내가 만든 결함)

Codex D-001을 검증하려고 "플레이어 공급 결정이 가격을 얼마나 움직이는가"를 측정하다가 발견했다.
동일 시드에서 공급폭탄(가동률 100%+지속 증설) vs 공급억제(가동률 55%+증설 0)를 비교했더니
**공급을 100배 늘린 쪽 가격이 더 높았다.**

원인은 `runQuarter()`의 부호다.

```js
const capacityPressure = clamp(actualSupplyQGrowth - trendQGrowth, -0.15, 0.15) * 0.25;
const dlnP = clamp(s.market.regimePerQuarterLogReturn + noise + capacityPressure, ...);
//                                                            ^^^ 더하고 있다
```

반응함수는 `ΔlnP = k + 2.7 × (-ln Sufficiency)`이고 `Sufficiency = Supply/Demand`다.
즉 **공급↑ → Sufficiency↑ → 가격↓**가 정설인데, 코드는 공급 증가율이 추세를 웃돌 때
`capacityPressure`를 양수로 만들어 **가격을 올린다**. 부호가 거꾸로다.

실측 (14개 시드, "공급폭탄 최종가 ÷ 공급억제 최종가", 1보다 크면 비정상):

| | 공급 늘렸는데 가격이 오른 시드 |
|---|---|
| 현재 구현 | **9 / 14** |
| 부호 수정(`+` → `-`) | **1 / 14** |

### 왜 이게 가장 심각한가

1. **게임의 중심 인과가 거꾸로다.** "공급과잉이 가격을 무너뜨린다"는 DRAM 사이클 게임의 존재 이유인데,
   현재 구현에서는 절반 이상의 시드에서 반대로 작동한다.
2. **Codex가 지적한 466% 전략 격차 WARN의 원인일 가능성이 높다.** 증설이 물량과 가격을 동시에 올려주니
   "공격증설"이 과보상된다. 부호만 고쳐도 격차가 **549% → 247%**로 떨어졌다(25시드 3전략 기준).
   완전 해결은 아니지만 밸런스 문제의 큰 부분이 이 버그였다.
3. **인과 가시화(양 안의 1순위)를 지금 만들면 거짓말을 하게 된다.** "증설했더니 가격이 올랐습니다"라는
   설명 카드를 성실하게 생성하게 된다. Codex가 "카피가 사실과 다른 원인을 주장하지 않도록 추적
   데이터에서 생성한다"고 쓴 그 원칙이, 추적 데이터 자체가 틀렸으면 무의미해진다.

### 부수 확인 — RNG는 문제없음

처음엔 "시장과 AI가 RNG 스트림을 공유해서 결정만 바꿔도 시장 경로가 통째로 바뀔 것"이라 의심했으나,
계측 결과 **동일 시드에서 rng 호출 횟수(47=47)와 정권 전개가 완전히 일치**했다. 이 가설은 기각한다.
따라서 Codex 0순위의 고정 시드 fixture는 예상보다 견고하게 만들 수 있다 — 좋은 소식이다.

## 4. 두 안의 대조 — 어디서 합의하고 어디서 물러서는가

### 이미 합의된 것 (양 안이 독립적으로 같은 결론)
- **인과 가시화가 최우선 재미 과제**다 (Claude 1순위 = Codex 1순위).
- **P0에 외부 바이너리 에셋을 넣지 않는다.** canvas/CSS/inline SVG와 텍스트로 먼저 검증한다.
  다만 Codex의 "에셋을 없애는 게 아니라 manifest로 관리해 나중에 교체 가능하게"가 내 신중론보다
  낫다 — 나는 "미루자"만 말했고 Codex는 미루면서도 교체 경로를 남겼다. Codex안 채택.
- **현재 빌드 구조(`src/*` → `build.js` → `index.html`) 유지**, Next.js/TS 이관은 보류.
- 비주얼/UX는 병행 프로토타입으로 간다.

### 내가 물러서는 것
1. **"완성된 룰셋" 전제 철회.** P0-A~E가 전부 확인된 이상 유지할 수 없다.
2. **Codex의 0순위(P0 테스트로 잠그기)를 양 안의 1순위보다 앞에 둔다.** 내 안에는 이 단계가 아예
   없었는데, P0-E를 감안하면 "틀린 인과 위에 인과 UI를 얹는" 최악의 순서가 될 뻔했다.
3. **첫 병행 프로토타입 주제: 팹 비주얼(내 제안) → 인과 카드(Codex 제안)로 양보.** Codex의 근거가
   더 강하다. 핵심 재미에 직접 연결되고 외부 에셋 없이 비교 가능하다. 내가 팹 비주얼을 제안한 이유는
   "로직과 파일이 안 겹쳐서 충돌이 적다"였는데, 이건 재미가 아니라 작업 편의 기준이었다.

### 아직 이견이 남는 것 — D-001 (시장 진실 원천)
Codex의 "제약된 하이브리드"(Sufficiency를 실제 공급·수요에서 계산하되 경계값을 둠) 방향에
**원칙적으로 동의**하되, 우선순위는 낮추자고 제안한다. 근거:

- P0-E 부호 수정만으로도 "내 공급 결정이 가격을 움직인다"는 인과는 **방향만큼은 올바르게** 성립한다
  (9/14 → 1/14). 하이브리드 엔진 재설계 없이도 인과 가시화와 플레이테스트를 시작할 수 있다.
- 반대로 하이브리드는 v0.2 개발 때 가격이 10^80까지 폭주했던 그 영역을 다시 건드리는 작업이라,
  잘못하면 지금 안정된 가격 경로를 잃는다. Codex도 "채택 전 현 방식과 동일 시드 비교가 필요하다"고
  단서를 달았는데, 그 비교 인프라(고정 시드 fixture)가 아직 없다.
- 따라서 **순서**를 제안한다: P0 버그 수정 → fixture 구축 → 그 fixture로 하이브리드를 A/B 비교 →
  그때 D-001 채택 여부 결정. 하이브리드를 버리자는 게 아니라, 검증 수단을 먼저 갖추자는 것이다.

안 보이는 구간이므로, S0+S1을 하나로 묶어 짧게 끝내고 S4를 빨리 시작하는 것을 권한다.

## 6. PM 결정이 필요한 항목 (양 안 통합)

Codex가 제기한 4건에 내 관점을 덧붙인다.

1. **1회 목표 플레이 시간** (Codex H-002, 권장 30~40분) — 40턴을 유지할지 축소할지가 여기서 갈린다.
2. **진영 실명 유지 여부** (H-004) — Codex는 실명 유지·공식 로고 보류를 권장. 나도 동의한다.
3. **첫 병행 프로토타입 주제** — 나는 인과 카드로 양보했으므로, 양 안이 인과 카드로 일치한다.
   PM이 반대하지 않으면 이대로 확정 가능.
4. **시대별 파산율 목표를 지금 정할지** (D-005) — 나는 **지금 정하지 말자**는 쪽이다. P0-E 수정만으로도
   파산율이 크게 달라질 것이므로, S2에서 새 기준선을 뽑은 뒤 정하는 게 순서상 맞다.

추가로 내가 제기하는 1건:

5. **S0(부호 수정)을 지금 바로 진행할지, 병행 프로토타입과 함께 시작할지.** 이 버그는 게임의 중심
   인과를 뒤집고 있어 방치하면 이후 모든 계측이 오염된다. PM 승인만 있으면 즉시 착수 가능하다.

## 7. 자기 비판 — Codex가 지적하지 않은 것

`README.md`와 PR #1 본문에 "지배 전략 부재(중앙값 기준 밴드 겹침)"를 **통과 항목으로 체크**해 두었는데,
정작 `validate.js`는 평균 기준으로 `WARN`을 출력하고 있었다. 서로 다른 지표를 근거로 통과를 주장한 셈이라
정확하지 않은 보고였다. Codex의 D-004(판정 지표 명문화)는 이 문제도 함께 해결한다.
