# DRAM 게임 공동 설계·개발 계획 v0.1

> 상태: Codex 상세 초안 — 합의안 작성 전
> 최종 결정권자: `PM`
> 초안 작성: `Codex`
> 필수 리뷰: `Claude`

## 0. 오늘의 목표

Human, Claude Code, Codex가 기존 v0.2 구현과 v0.4 설계를 출발점으로 다음 네 가지를 1차 합의한다.

1. 어떤 플레이 경험을 만들 것인가.
2. 그 경험에 필요한 게임 시스템·데이터·시청각 에셋은 무엇인가.
3. 프로토타입을 어떤 구조로 제품화할 것인가.
4. 누가 제안·구현·검증·최종 결정할 것인가.

오늘은 설계와 분장까지가 범위다. 합의되지 않은 기능 구현과 에셋 제작은 시작하지 않는다.

## 1. 전제와 아직 결정하지 않은 것

### 현재 전제

- `main`의 v0.2는 폐기 대상이 아니라 **행동 가능한 기준선**이다.
- 핵심 재미는 “불확실한 시장에서 지금 결정하고, 수년 뒤 결과를 감당하는 것”이다.
- 산업 지식이 없는 플레이어도 인과를 이해할 수 있어야 하며, 전문가는 얕다고 느끼지 않아야 한다.
- 현실성은 숫자의 정밀함보다 의사결정의 방향과 트레이드오프가 사실적인지를 우선한다.
- 모든 신규 시스템은 `생산성`, `믹스`, `시장`, `경쟁 반응` 중 하나에 귀속되고 플레이어 결정에 영향을 줘야 한다.

## 2. 재미를 만드는 다섯 기둥

| 재미 기둥 | 플레이어가 느껴야 할 것 | 핵심 메커니즘 | 1차 검증 기준 |
|---|---|---|---|
| 장기 베팅 | “지금 투자할까, 한 사이클 기다릴까?” | 12분기 노드 리드타임, 증설 지연, Ramp Valley | T12~T20에 노드 전환 고민이 반복 발생 |
| 기회비용 | “HBM이 좋아도 전부 넣을 수는 없다” | HBM trade ratio, 컨벤셔널 포기 매출, 현금 제약 | 한 레버가 항상 최선이 아닌 선택 분포 |
| 불확실성 속 판단 | “신호는 보이지만 확신할 수 없다” | 노이즈 낀 Sufficiency, 정권 지속기간 비대칭 | 사후에는 결과를 설명할 수 있으나 사전 정답은 없음 |
| 경쟁사의 성격 | “회사마다 다음 행동을 읽는 맛이 있다” | 행동편향, 뉴스, 관성, 상대 노드/HBM 게이트 | 블라인드 플레이테스트에서 경쟁사 성향 구분 |
| 나만의 산업 서사 | “내 결정 때문에 이 회사의 10년이 이렇게 됐다” | 결정 타임라인, 원인→결과 회고, 위기·반등 | 종료 후 플레이어가 핵심 결정 2개 이상 회상 |

재미를 추가할 때는 기능 수보다 `예고 → 결정 → 대기 → 결과 공개 → 해석`의 연출 품질을 먼저 높인다.

### P0 — 설계 검증과 버티컬 슬라이스에 필수

| 데이터 | 시장·노드·원가 파라미터 원본표 | CSV/JSON, 출처·단위·신뢰도 필드 필수 | `PM` 출처 승인 |
| 콘텐츠 | 용어집과 첫 8턴 튜토리얼 문구 | 한국어 원문, 한 문장 45자 안팎 | `Codex` 초안 |
| 검증 | 고정 시드·결정 로그·기대 결과 fixture | 재현 가능하고 UI 없이 실행 가능 | `Claude` |

### P1 — 재미와 전달력을 높이는 에셋

- 경쟁사별 추상 초상 또는 기업 성격 카드. 공식 로고 사용 여부가 정해지기 전에는 비브랜드 형태로 제작한다.
- 투자 승인, 장비 반입, 퀄 통과, 수율 램프, 공급과잉을 보여주는 5종 이벤트 카드.
- 결정 후 3년을 기다리는 동안 진행 상황을 보여주는 팹 공정 단계 연출.
- 상승·하락 정권의 서로 다른 UI 모션과 짧은 효과음.
- 10년 종료 시 의사결정 타임라인과 “원인 → 결과” 회고 화면.

### P2 — 핵심 루프 검증 뒤 검토

- 배경 음악, 고해상도 일러스트, 다국어 음성, 모바일 전용 에셋.
- NAND, 지정학, EUV 슬롯 등 현재 보류된 시스템 전용 에셋.

에셋마다 `목적`, `노출 화면`, `상태 수`, `크기`, `포맷`, `저작권/출처`, `담당`, `승인자`를 기록한다.

## 4. 개발 구조 — PM 결정 반영

현재 마일스톤에서는 Next.js/TypeScript로 이관하지 않는다. Claude가 `main`에서 완료한 소스 분리 구조를
공동 기준으로 사용한다.

```text
src/core.js                # DOM 비의존 시뮬레이션 코어
src/ui.js                  # 화면·입력·canvas
src/styles.css             # 스타일
template.html              # 배포물 골격
build.js                   # 외부 의존성 없는 결합 스크립트
validate.js                # src/core.js 직접 검증
index.html                 # 커밋되는 단일 파일 배포물
```

인과 설명과 뉴스 시스템을 구현할 때는 `src/events.js` 또는 `src/trace.js`처럼 책임이 분명한 파일을
추가하고 `build.js`가 결합하게 한다. 소스 수정 뒤 `node build.js`와 `node validate.js`를 모두 실행한다.
프레임워크·TypeScript 이관은 핵심 재미 플레이테스트 뒤 별도 결정으로 보류한다.

## 5. 1차 업무분장

담당 이름은 `PM` / `Claude` / `Codex`로 고정하고, 실제 모델명은 작업이력에 별도로 적는다.

### `PM` — 제품 책임자·크리에이티브 디렉터

- 타깃 유저, 플레이 시간, 현실성 수준, 최종 재미 기준 결정.
- 실측 자료·기업 표현·브랜드 사용 승인.
- 두 에이전트의 상충 제안 중 최종 선택.
- 직접 플레이테스트와 정성 피드백 제공.

### `Claude` — 기준 구현·독립 프로토타입

- 자신이 작성한 v0.2의 의도와 실제 동작 차이 설명.
- 고정 시드 회귀 테스트, 수치 안정성, 상태 전이, 성능 담당.
- TypeScript 코어 이관과 기존 결과 비교.
- Codex와 같은 문제를 별도 브랜치에서 독립적으로 시도하고 구현 가능성을 검증.

### `Codex` — 독립 프로토타입·설계 감사

- 설계 문서 통합, 결정사항과 구현 간 추적성 관리.
- 재미 가설, UX 흐름, 에셋 명세, 플레이테스트 기준 작성.
- Claude와 같은 문제를 다른 접근으로 프로토타이핑하고 비교 근거 제공.
- 구현과 문서의 불일치 감사 및 재현 절차 작성.

### 교차 검토 규칙

| 작업 유형 | 주담당 | 필수 리뷰 | 최종 승인 |
|---|---|---|---|
| 게임 비전·스코프 | `PM` | 두 에이전트 | `PM` |
| 수치 모델·시뮬레이션 구현 | `Claude` | `Codex` 독립 검토 | `PM` |
| 재미·UX 병행 프로토타입 | `Claude` + `Codex` 각자 | 상호 비교 | `PM` |
| 사실·출처·기업 표현 | 조사 담당 에이전트 | 다른 에이전트 | `PM` |
| 테스트 통과 판정 | 구현하지 않은 에이전트 | 주담당 | `PM` |

동일 파일을 두 에이전트가 동시에 편집하지 않는다. 각 작업은 한 명의 주담당과 한 명의 리뷰어를 둔다.

## 7. 작업이력 기록 규칙

모든 의미 있는 작업은 `docs/worklog.md`에 다음 항목을 남긴다.

```text
날짜 / 작업 ID / 제목 / 상태
요청·최종 결정: Human 또는 에이전트 ID
주담당: 에이전트 ID
실행 제품·모델: 확인 가능한 정확한 이름, 모르면 “미기록”
리뷰어: 에이전트 ID 또는 “대기”
입력: 사용한 문서·데이터·커밋
변경·판단: 무엇을 했고 왜 했는지
검증: 명령, 시드, 플레이테스트 또는 문서 리뷰
미결 사항: 다음 결정권자와 질문
산출물: 파일, 커밋, PR
```

제안자와 구현자가 다르면 둘 다 기록한다. Human의 구두 결정도 작업 ID와 함께 남긴다. 모델명이 불명확할 때
추측하지 않으며, 에이전트 ID만으로 책임 주체를 유지한다.
