# 개발 계획안 — Codex (반/反, 독립안)

> 작업 ID: `X-PLAN-002`
> 작성: `Codex`
> 상태: Claude안과 합의 전 독립안
> 상세 근거: `design-audit-v0.2-v0.4.md`, `design-v0.5-draft.md`, `asset-spec-v0.1.md`

이 문서는 Codex가 Claude의 `plan-claude.md`를 읽기 전에 작성한 설계·감사 자료를 현재 PM 결정과 저장소
구조에 맞춰 압축한 독립안이다. 두 안의 합의는 별도 `plan-synthesis.md`에서 진행한다.

## 핵심 논지

v0.2는 플레이 가능한 기준선이지만 “완성된 룰셋”으로 고정하기에는 검증 근거가 부족하다. 동시에 전면적인
시장 엔진 재설계나 프레임워크 이관은 캐주얼 유저의 재미를 증명하기 전에 하기에는 너무 비싸다.

따라서 다음 세 가지를 함께 진행해야 한다.

1. 플레이어가 결정과 결과의 인과를 이해하게 만든다.
2. 재미 판단을 왜곡할 수 있는 최소한의 P0 규칙·검증 불일치만 테스트로 잠근다.
3. 실제 사람 플레이테스트로 재미 가설을 검증한 뒤 엔진 정밀화 여부를 결정한다.

## 근거가 된 현재 기준선

2026-08-22 `node validate.js` 재실행 결과:

- 전략 평균 점수 격차 466% — 스크립트 판정 WARN.
- 진영 최고점 독점은 삼성 8/15로 PASS.
- 성장둔화기 균형형 파산율 47% — 스크립트 자체 재검토 문구의 25%를 초과.
- 첫 노드 전환 중앙값 T5 — 설계 목표 T12~T20보다 빠름.

추가로 Ramp Valley가 실질 1분기만 적용될 가능성, UI의 3개 결정 제한을 검증 전략이 우회하는 문제,
HBM 배분 없이 퀄 시간이 누적되는 문제를 코드 감사에서 발견했다. 상세 내용은
`design-audit-v0.2-v0.4.md`에 있다.

## 제안 우선순위

### 0순위 — 기준선과 P0 실패 테스트

- 고정 시드 결과 fixture를 만든다.
- Ramp Valley 2분기, 결정 3개 제한, HBM 퀄 조건을 실패 테스트로 재현한다.
- 이 단계에서는 시장 모델이나 밸런스 상수를 재설계하지 않는다.

### 1순위 — 결정→결과 인과 가시화

각 결정에 ID와 예상 완료 턴을 부여하고, 분기 결과가 어떤 결정·시장 변화·경쟁 반응에서 왔는지 추적한다.
화면에는 모든 계산을 노출하지 않고 가장 큰 원인 1~2개와 상세 보기만 보여준다.

### 2순위 — 플레이테스트 계측

고정 시드에서 결정, 되돌림, 프로젝트 시작·완료, 국면 변화, 현금 위기, 종료 결과를 로컬 JSON으로 남긴다.
6명의 1차 테스트에서 노드 전환 고민, HBM 되돌림, 원인 이해, 경쟁사 구분, 재도전 의향을 측정한다.

### 3순위 — 뉴스·경쟁사·긴장감

인과 추적 데이터를 이용해 경쟁사 발표와 실제 crossover의 시차, 파산 카운트다운, 퀄 통과, 공급과잉 등을
뉴스와 상태 연출로 보여준다. 카피가 사실과 다른 원인을 주장하지 않도록 추적 데이터에서 생성한다.

### 4순위 — 비주얼 병행 프로토타입

Claude와 Codex가 같은 화면을 별도 브랜치에서 독립적으로 제안하고 PM이 선택한다. 첫 후보는 팹 전체
리디자인보다 “분기 결과 인과 카드”다. 핵심 재미에 직접 연결되고 외부 에셋 없이 비교할 수 있기 때문이다.

## 개발 구조

PM이 결정하고 Claude가 구현한 현재 구조를 유지한다.

```text
src/core.js + src/ui.js + src/styles.css + template.html
  → node build.js
  → index.html
```

- 인과 데이터는 `src/trace.js`, 사건 카피는 `src/events.js` 분리를 우선 검토한다.
- 모든 소스는 `build.js`로 단일 HTML에 인라인한다.
- 소스 변경 뒤 `node build.js`와 `node validate.js`를 실행한다.
- Next.js/TypeScript 이관은 사람 플레이테스트 뒤 별도 의사결정으로 보류한다.

## 에셋 입장

P0에는 외부 바이너리 에셋을 넣지 않는다. canvas, CSS, inline SVG와 텍스트로 상태 전달을 먼저 검증한다.
다만 에셋을 “없애는” 것이 아니라 ID, 목적, 상태, 제작자, 라이선스를 manifest로 관리해 나중에 교체할 수
있게 한다. 공식 로고, 고해상도 이미지, 배경음은 PM의 브랜드 결정과 핵심 루프 검증 뒤로 미룬다.

| 영역 | 방식 |

| 제품 방향·최종 채택 | PM |

## PM 결정이 필요한 항목

1. 1회 목표 플레이 시간.
2. 기업 실명과 공식 로고 사용 범위.
3. 첫 병행 프로토타입을 인과 카드로 할지 팹 비주얼로 할지.
4. 시대별 목표 파산율을 지금 정할지 플레이테스트 뒤 정할지.

## Codex안 완료 기준

- P0 테스트가 현재 결함을 재현한다.
- 인과 카드 두 시안을 PM이 비교할 수 있다.
- 1차 플레이테스트 결과가 `playtest-plan-v0.1.md` 기준으로 기록된다.
- 그 결과에 따라 엔진 재설계와 비주얼 투자 우선순위를 다시 결정한다.
