# 팀 운영 계획 — DRAM 사이클 시뮬레이터

이 문서는 살아있는 문서(living doc)다. 매 세션마다 갱신되며, "누가 무엇을 왜 맡았는지"의 최신 상태를
담는다. 실제로 일어난 일의 이력은 `docs/worklog.md`에 별도로 남는다.

- **작성일**: 2026-08-22
- **상태**: 1차 초안 — PM 확인 필요 항목은 맨 아래 별도 섹션에 정리

## 1. 팀 구성

| 이름 | 역할 | 비고 |
|---|---|---|
| **PM** (사용자) | 게임 방향성 최종 결정, 우선순위 승인, Claude/Codex 산출물 검수 | 유일한 최종 의사결정권자 |
| **Claude** (Claude Code) | 지금까지 시뮬레이션 코어 구현·버그 수정·밸런싱·검증 담당 | 이 세션 |
| **Codex** | 역할 미정 — 아래 "PM 확인 필요" 참고 | 별도 세션/도구로 운영 |

이름 규칙: 문서·커밋·이슈 어디서든 담당자를 `PM` / `Claude` / `Codex`로만 표기한다(모델 버전 붙이지 않음 —
세션이 바뀌어도 역할 이름은 고정). 협업 항목은 `PM+Claude`처럼 표기.

## 2. 현재 상태 스냅샷 (기술 자산 기준)

- `index.html`: 단일 파일 게임 본체. 시장/생산성/믹스 엔진 + 경쟁 AI 3사 구현 완료(v0.2 스코프).
  비주얼은 canvas 도형(사각형/색상)으로만 그려져 있음 — 실제 아트 에셋은 0개.
  UI 텍스트는 전부 한국어(하드코딩), 사운드 없음, 폰트는 시스템 monospace.
- `validate.js`: 순수 로직 검증용 몬테카를로 스크립트. 게임 재미 자체는 검증하지 않음(밸런스만 검증).
- 설계 문서(`design-v0.4.md`)에 언급된 원본 팹 픽셀아트 프로토타입(`fab-lifecycle-pixel.html`)은
  이번 세션에 파일로 제공되지 않아 미확보 — 참고할 실제 에셋이 아예 없는 상태에서 시작함.

즉 지금은 "룰은 완성됐지만 룩앤필과 서사적 재미는 거의 없는" 단계.

## 3. 필요한 에셋 목록 (1차 브레인스토밍)

우선순위는 게임성 전략(4절)이 확정된 뒤에 정하는 게 맞지만, 종류별로 무엇이 필요할지 먼저 나열한다.

### 3.1 비주얼
- 팹 실루엣/라인 그래픽 — 현재 canvas 사각형으로 임시 처리 중. 원본 픽셀아트 프로토타입이 있다면
  그 스타일을 이식, 없다면 새로 정의 필요 (도트/픽셀아트 vs 플랫 벡터 vs 순수 데이터시각화 중 톤 결정 필요).
- 진영 4종 로고/컬러 아이덴티티 (SK하이닉스/삼성/마이크론/CXMT를 실명 그대로 쓸지, 가상 브랜드명으로
  바꿀지도 결정 필요 — 상표/라이선스 리스크 검토 대상)
- 국면(4종)·이벤트 아이콘 세트
- 노드 세대별 팔레트(이미 6세대분 hex 코드는 있음 — `NODE_COLORS`), 다만 "팔레트 스왑"이 실제
  디테일 있는 스프라이트에 적용될 에셋 자체가 없음
- UI 아이콘 6종(레버) — 현재 텍스트 라벨만 있음
- 엔딩/타이틀 화면 일러스트(선택)

### 3.2 사운드 (현재 전무)
- 턴 진행 클릭/컨펌 SFX
- 국면 전환 알림음(특히 "타이트→극단타이트" 같은 위험 신호)
- 파산 경고/카운트다운 스팅어
- 승리/엔딩 스팅어
- (선택) 배경음 루프 — 국면별로 분위기 다르게 갈 수도 있음

### 3.3 텍스트/카피
- 온보딩·튜토리얼 문구 (현재 전무 — 시작화면에 설명 한두 줄뿐)
- 뉴스 이벤트 텍스트 뱅크 — 현재 국면전환/파산 2종류뿐. 설계문서 Q39(발표 vs 실질 crossover 정보
  비대칭), 경쟁사 노드 전환 announcement, 지정학 플레이버 등 다양화 필요
- 엔딩 스크린 진영별 플레이버 텍스트
- (다국어 대응 시) 영어 UI 번역 텍스트 전체

### 3.4 데이터

## 4. 개발 구조 제안

### 4.1 유지할 원칙 (핸드오프 문서 명시 사항, 변경 불가)
- 배포물은 **단일 HTML 파일**, 외부 프레임워크 없음.
- 시뮬레이션 코어는 DOM 비의존 순수 함수(`runQuarter`)로 UI와 분리, `SIM_START/END` 마커로 추출 가능해야 함.

### 4.2 논의가 필요한 구조적 결정
- **소스 분리 여부**: 지금은 `index.html` 안에 코어+UI가 전부 들어있어 두 명(Claude+Codex)이
  동시에 건드리면 병합 충돌 가능성이 높다. 개발 중에는 `core.js` / `ui.js` / `assets/` 등으로
  소스를 나누고, 빌드 스크립트(esbuild 등, 의존성 최소)로 최종에만 단일 HTML로 합치는 방식을
  고려할 만하다. 다만 "빌드 없는 단일 파일"이 원래 설계 제약이었으므로 이 결정은 PM 승인이 필요.
- **동시 작업 시 브랜치 전략**: 지금은 사용자 요청으로 `main`에 직접 커밋 중. Claude와 Codex가
  동시에 작업하게 되면 같은 파일(`index.html`) 충돌 위험이 커진다. 두 에이전트가 서로 다른 영역
  (예: 로직 vs 비주얼)을 맡더라도 파일이 하나라 물리적으로 충돌 가능 — 4.2의 소스 분리 결정과
  맞물려 있음.
- **테스트 전략**: `validate.js`(밸런스 몬테카를로) 외에 개별 함수 단위 테스트가 없음. 로직을 여러
  사람이 만지기 시작하면 회귀 방지용 유닛 테스트가 필요해진다.
- **다음 마일스톤 스코프(v0.3)**: design-v0.4 §7에서 의도적으로 보류한 항목들(LTA 캡, 이중 트랙
  가격, Cross-impact Matrix, NAND, 지정학 이벤트, EUV 슬롯) 중 무엇을 언제 되살릴지 아직 미정.

## 5. 게임성 확보 전략 (초안 — PM 방향 확정 필요)

현재 게임은 규칙은 완성됐지만 "경영 스프레드시트"에 가깝고, 재미 장치가 약하다. 방향을 정하기 전에
**타겟 유저**부터 확정해야 아래 우선순위가 갈린다 (교육/시뮬레이션 성격 vs 캐주얼 경영 게임 성격).
그 결정을 전제로, 저비용/고비용 순으로 아이디어를 나열한다.

### 저비용 (텍스트/로직만으로 가능, 에셋 불필요)
- 뉴스 이벤트 다양화 — 경쟁사 announcement와 실질 crossover 사이 정보 비대칭 연출(design-v0.4 §4.1
  "Tech Crossover"는 설계에 있지만 미구현)
- 결정↔결과 인과를 명시적으로 보여주는 배지 ("이번 분기 매출 하락의 절반은 3턴 전 HBM 배분 축소 때문")
- 파산 위기 카운트다운 시각/문구 강화 (지금은 조용히 4분기 세다가 끝남)
- 진행 중 경쟁사 대비 순위/격차 상시 노출 (지금은 엔딩에만 표시)
- 업적/도전과제 텍스트 리스트 (예: "성숙기에서 파산 없이 완주", "HBM 매출 비중 50% 달성")

### 중비용 (약간의 비주얼/애니메이션 필요)
- 팹 캔버스를 실제 스프라이트 기반으로 교체 (지금은 사각형 도형)
- 국면 전환 시 화면 전체 톤 변화(경고색 플래시 등)로 긴장감 연출
- 사운드 SFX 추가(클릭, 국면 알림, 파산 경고)

### 고비용 (콘텐츠 제작 규모)
- 진영별 서사/엔딩 컷신 텍스트 확장
- 다국어(영어) 전체 번역 + 로케일 전환
- 배경음악

## 6. 업무 분장 1차안

**원칙**: 지금까지 Claude가 로직·검증을 맡아왔으니 그 연속선을 유지하고, Codex는 PM이 원하는 역할에
따라 배정한다(옵션 3가지를 6.1에 제시). PM은 방향 결정·검수를 전담한다.

| 영역 | 1차 담당(안) | 근거 |
|---|---|---|
| 시뮬레이션 로직/밸런싱/검증 | Claude | 지금까지 해온 작업의 연속, `validate.js` 이미 이 워크플로우로 구성됨 |
| 비주얼/에셋(캔버스 아트, 아이콘, UI 폴리시) | Codex (안) | 아래 6.1 옵션에 따라 확정 |
| 게임성/서사 콘텐츠(뉴스 이벤트, 카피) | Claude/Codex 분담 가능, PM 검수 필수 | 톤앤매너는 PM 승인 필요 |
| 방향성/우선순위/최종 승인 | PM | 유일 결정권자 |
| 회귀 검증(몬테카를로 + 유닛 테스트) | Claude | 기존 인프라 소유자 |

### 6.1 Codex 역할 옵션 (PM 결정 필요)
1. **레이어 분담형**: Codex가 비주얼/UI/에셋 파이프라인 전담, Claude는 로직/밸런싱 전담. 병렬 작업
   가능하지만 4.2의 파일 충돌 문제를 먼저 해결해야 함(소스 분리 또는 순번제 작업).
2. **상호 검증형**: Codex가 Claude의 로직/밸런싱 산출물을 독립적으로 리뷰(2차 몬테카를로, 코드
   리뷰) — 충돌 위험은 낮지만 개발 속도는 레이어 분담형보다 느림.
3. **병행 프로토타입형**: 같은 문제(예: 게임성 강화)를 Claude/Codex가 각자 다른 접근으로 시도하고
   PM이 비교해서 채택 — 실험 비용은 높지만 품질/재미 옵션을 넓게 탐색 가능.

## 7. PM 확인 필요 (오픈 이슈)

1. **Codex의 역할**: 위 6.1의 세 옵션 중 무엇으로 시작할지, 혹은 다른 방식인지.
2. **타겟 유저**: 반도체 업계 관계자 대상 교육/시뮬레이션 톤 vs 일반 유저 대상 캐주얼 경영 게임 톤 —
   4절의 게임성 전략 우선순위가 여기서 갈린다.
3. **소스 분리 + 빌드 도입 여부**: "빌드 없는 단일 HTML" 원칙을 유지한 채 두 에이전트가 동시 작업할
   방법을 찾을지, 아니면 개발 중엔 소스를 나누고 배포 시점에만 합칠지.
4. **진영 실명 사용**: SK하이닉스/삼성/마이크론/CXMT 실명을 계속 쓸지, 가상 브랜드명으로 바꿀지
   (상표/브랜드 리스크 관점에서 PM 판단 필요).
5. **원본 팹 픽셀아트 프로토타입**(`fab-lifecycle-pixel.html`) 파일을 구할 수 있는지 — 있으면
   비주얼 방향을 처음부터 다시 잡지 않아도 됨.
