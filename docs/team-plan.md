## 2. 현재 상태 스냅샷 (기술 자산 기준)

- `src/core.js` + `src/ui.js` + `src/styles.css` → `node build.js` → `index.html`(커밋되는
  플레이 가능한 산출물). 시장/생산성/믹스 엔진 + 경쟁 AI 3사 구현 완료(v0.2 스코프).
  비주얼은 canvas 도형(사각형/색상)으로만 그려져 있음 — 실제 아트 에셋은 0개.
  UI 텍스트는 전부 한국어(하드코딩), 사운드 없음, 폰트는 시스템 monospace.
- `validate.js`: 순수 로직 검증용 몬테카를로 스크립트. `src/core.js`를 직접 읽는다(빌드 불필요).
  게임 재미 자체는 검증하지 않음(밸런스만 검증).
- 설계 문서(`design-v0.4.md`)에 언급된 원본 팹 픽셀아트 프로토타입(`fab-lifecycle-pixel.html`)은
  이번 세션에 파일로 제공되지 않아 미확보 — 참고할 실제 에셋이 아예 없는 상태에서 시작함.

즉 지금은 "룰은 완성됐지만 룩앤필과 서사적 재미는 거의 없는" 단계.

## 3. 필요한 에셋 목록 (1차 브레인스토밍)

우선순위는 게임성 전략(4절)이 확정된 뒤에 정하는 게 맞지만, 종류별로 무엇이 필요할지 먼저 나열한다.

  그 스타일을 이식, 없다면 새로 정의 필요 (도트/픽셀아트 vs 플랫 벡터 vs 순수 데이터시각화 중 톤 결정 필요).

## 4. 개발 구조 제안

### 4.1 유지할 원칙 (핸드오프 문서 명시 사항, 변경 불가)
- 배포물은 **단일 HTML 파일**, 외부 프레임워크 없음.
- 시뮬레이션 코어는 DOM 비의존 순수 함수(`runQuarter`)로 UI와 분리, `SIM_START/END` 마커로 추출 가능해야 함.

### 4.2 소스 분리 + 빌드 (결정됨, 구현 완료)
`src/core.js`(SIM_START/END 마커 유지) / `src/ui.js` / `src/styles.css` + `template.html` →
`node build.js`(외부 의존성 없는 순수 Node 스크립트, esbuild 등 번들러 미사용 — core/ui가 이미
`window.DramSimCore` 전역 참조로만 통신하므로 단순 문자열 접합으로 충분) → `index.html`.
`index.html`은 계속 커밋해 빌드 없이 바로 플레이 가능하게 유지한다 — 소스를 고친 뒤에는
반드시 `node build.js`를 실행하고 나서 커밋할 것.

- **동시 작업 시 브랜치/충돌 전략 (결정됨)**: Codex가 실제로 투입되면서 확정됨 — `main`은 안정된
  공유 베이스로 유지하고, 각자 자기 작업방 브랜치에서 작업한다.
  - `claude/dev` — Claude 작업 브랜치
  - `codex/design-v0.5` — Codex 설계·계획 브랜치. 후속 구현도 작업별 `codex/...` 브랜치 사용
  - `main` 직커밋은 여기서 중단하고, 이후 변경은 각 브랜치에 쌓다가 PM 검토 후 머지(또는 PR)로
    합류한다. 두 브랜치가 같은 파일(`index.html`, `src/*`)을 건드리면 머지 시 충돌 가능성은
    여전히 있으니, 가능하면 서로 다른 영역/파일을 건드리는 작업부터 병행하는 게 안전하다
    (예: Claude=`src/core.js`+`src/ui.js`의 로직·이벤트 영역, Codex=비주얼/에셋 영역).
- **테스트 전략**: `validate.js`(밸런스 몬테카를로) 외에 개별 함수 단위 테스트가 없음. 로직을 여러
  사람이 만지기 시작하면 회귀 방지용 유닛 테스트가 필요해진다.
- **다음 마일스톤 스코프(v0.3)**: design-v0.4 §7에서 의도적으로 보류한 항목들(LTA 캡, 이중 트랙
  가격, Cross-impact Matrix, NAND, 지정학 이벤트, EUV 슬롯) 중 무엇을 언제 되살릴지 아직 미정.

## 5. 게임성 확보 전략 (타겟 유저 = 일반 캐주얼 경영게임 유저, 결정됨)

현재 게임은 규칙은 완성됐지만 "경영 스프레드시트"에 가깝고, 재미 장치가 약하다. 타겟 유저가
**일반 캐주얼 경영게임 유저**로 확정됐으므로, 실측 정확도보다 **재미·몰입·서사**를 우선한다 —
즉 아래 목록 중 "저비용"에 있는 재미 장치들(뉴스 이벤트, 인과 배지, 긴장감 연출, 업적)을
정밀 캘리브레이션(경쟁 AI 초기값 재보정, 노드 곡선 정밀화 등)보다 먼저 다룬다.
저비용/고비용 순으로 아이디어를 나열한다.

### 저비용 (텍스트/로직만으로 가능, 에셋 불필요)
- 뉴스 이벤트 다양화 — 경쟁사 announcement와 실질 crossover 사이 정보 비대칭 연출(design-v0.4 §4.1
  "Tech Crossover"는 설계에 있지만 미구현)
- 결정↔결과 인과를 명시적으로 보여주는 배지 ("이번 분기 매출 하락의 절반은 3턴 전 HBM 배분 축소 때문")
- 파산 위기 카운트다운 시각/문구 강화 (지금은 조용히 4분기 세다가 끝남)
- 진행 중 경쟁사 대비 순위/격차 상시 노출 (지금은 엔딩에만 표시)
- 업적/도전과제 텍스트 리스트 (예: "성숙기에서 파산 없이 완주", "HBM 매출 비중 50% 달성")

### 중비용 (약간의 비주얼/애니메이션 필요)
- 팹 캔버스를 실제 스프라이트 기반으로 교체 (지금은 사각형 도형)
- 국면 전환 시 화면 전체 톤 변화(경고색 플래시 등)로 긴장감 연출
- 사운드 SFX 추가(클릭, 국면 알림, 파산 경고)

### 고비용 (콘텐츠 제작 규모)
- 진영별 서사/엔딩 컷신 텍스트 확장
- 다국어(영어) 전체 번역 + 로케일 전환
- 배경음악

## 6. 업무 분장 1차안

**원칙**: Codex는 **병행 프로토타입형**(6.1)으로 운영 — 같은 문제를 Claude와 독립적으로 시도하고
PM이 비교해 채택한다. 따라서 아래 표의 "담당"은 배타적 소유가 아니라 "누가 먼저/기본으로
시도하는지"에 가깝고, 게임성처럼 재미가 걸린 영역은 의도적으로 Claude/Codex 둘 다 시도 대상이다.

| 영역 | 1차 담당(안) | 비고 |
|---|---|---|
| 시뮬레이션 로직/밸런싱/검증 | Claude | 지금까지 해온 작업의 연속, `validate.js` 이미 이 워크플로우로 구성됨 |
| 비주얼/에셋(캔버스 아트, 아이콘, UI 폴리시) | Claude + Codex 병행 | 재미가 가장 크게 걸린 영역이라 두 접근 다 보고 싶음 |
| 게임성/서사 콘텐츠(뉴스 이벤트, 카피) | Claude + Codex 병행 | 톤앤매너는 PM 승인 필수 |
| 방향성/우선순위/최종 승인, 병행 산출물 비교·채택 | PM | 유일 결정권자 |
| 회귀 검증(몬테카를로 + 유닛 테스트) | Claude | 기존 인프라 소유자 — Codex 산출물도 병합 전 이 검증을 통과해야 함 |

### 6.1 Codex 운영 방식 (결정됨: 병행 프로토타입형)
같은 문제(예: 팹 비주얼 리디자인, 뉴스 이벤트 시스템)를 Claude/Codex가 각자 다른 브랜치에서
독립적으로 시도하고, PM이 비교해서 채택하거나 좋은 부분만 골라 합친다. 실험 비용은 높지만 품질/재미
옵션을 넓게 탐색할 수 있다. 첫 주제는 PM이 **분기 결과 인과 카드 UI**로 확정했다. Claude와 Codex는
동일한 목표와 비교 기준으로 독립 시안을 만들고, PM이 이해도·재미·정보 밀도·인과 정확성을 비교한다.
