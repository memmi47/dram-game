# 개발 계획안 — Claude (정/正, 1차 초안)

정-반-합 토론용 문서. Codex의 안(`docs/plan-codex.md`, 별도 추가 예정)과 대조 토론 후
`docs/plan-synthesis.md`로 합의안을 만든다. 이 문서는 **Codex 안을 보지 않은 상태**에서 독립적으로
작성했다 — 서로 영향받지 않은 안 두 개를 먼저 만드는 게 진짜 토론이 되기 때문.

전제: `docs/team-plan.md`의 PM 결정(타겟=캐주얼 경영게임 유저, 재미>정확도, Codex=병행 프로토타입형)을
그대로 따른다. 여기서는 그 위에서 **무엇을 먼저 만들지, 왜 그 순서인지**에 대한 내 입장을 낸다.

---

## 핵심 논지

지금 엔진(시장/생산성/믹스 엔진 + 경쟁 AI)은 몬테카를로 검증까지 통과한 **완성된 룰셋**이다.
캐주얼 유저를 재미있게 하는 데 병목은 룰의 정교함이 아니라 — **"내 결정이 왜 이 결과를 냈는지
플레이어가 화면만 보고 알 수 있는가"**다. 이건 design-v0.4.md 0절의 두 번째 불변 원칙
("결정과 결과 사이의 인과가 화면에서 보여야 한다")이기도 한데, 지금 구현은 이 원칙을 사실상
지키지 못하고 있다 — 히스토리 로그는 쌓이지만 "왜"를 설명해주지 않는다.

그래서 내 우선순위는 **엔진을 더 정밀하게 만들거나 아트를 화려하게 만드는 것보다, 이미 있는 룰 위에
"인과를 보여주는 얇은 서사 레이어"를 먼저 얹는 것**이다. 비용 대비 재미 기여도가 가장 높다고 본다.

## 제안 우선순위 (순서에 근거 포함)

### 1순위 — 결정→결과 인과 가시화 (저비용, 순수 로직+텍스트)
지금은 "이번 분기 매출이 줄었다"만 보이고 "왜"가 안 보인다. 매 턴 결과 화면에 "이번 분기 변화의
주 원인" 배지를 1~2개 자동 생성해서 보여준다 (예: "매출 -18%: 3턴 전 결정한 Ramp Valley 진행 중",
"영업이익 흑자 전환: 국면이 타이트로 전환 + 가동률 95%"). 순수하게 `lastFin`/`lastProd`/`market`
상태를 비교해서 텍스트로 합성하는 로직이라 에셋 없이 바로 구현 가능하다. **이걸 1순위로 두는 이유는
"재미 추가"가 아니라 설계 문서가 이미 요구한 핵심 원칙의 미이행 항목을 채우는 것이기 때문** — 다른
어떤 재미 요소보다 근거가 명확하다.

### 2순위 — 뉴스 이벤트 다양화 (저비용, 텍스트 중심)
지금 뉴스피드는 국면전환/파산 단 2종류뿐이라 "세계가 살아있다"는 느낌이 없다. design-v0.4.md
§4.1의 Tech Crossover(경쟁사 노드 전환 발표 vs 실질 전환 시점의 정보 비대칭 — 이미 설계에 있지만
미구현)부터 시작해서, 경쟁사 증설/전환 announcement, 시장 화제성 이벤트 등 최소 10종 이상의 텍스트
이벤트 뱅크를 만든다. 캐주얼 유저에게는 정밀한 경제 시뮬레이션보다 "이야기가 진행 중이다"라는 감각이
리텐션에 더 크게 기여한다고 본다.

### 3순위 — 긴장감 연출 (저비용~중비용)
파산 카운트다운(4분기 중 몇 번째인지 지금은 조용히 셈), 국면 전환 임박 신호 같은 것들. 로직은 이미
있으니 화면 연출(색상/애니메이션)만 얹으면 된다.

### 4순위 — 팹 비주얼 리디자인 (중비용, 병행 프로토타입 적합)
지금 canvas 사각형 도형을 실제 스프라이트/디테일 있는 그래픽으로. **이 항목을 Claude/Codex 병행
프로토타입의 첫 주제로 제안한다** — 이유: (a) 로직을 건드리지 않아 다른 작업과 충돌 위험이 낮고,
(b) "재미"에 대한 정답이 없어 두 가지 다른 시안을 보고 PM이 고르는 게 실제로 유용하며, (c) 1~3순위
작업과 파일이 겹치지 않아(비주얼은 `src/ui.js`의 `drawFab` 함수 영역, 인과/이벤트는 새 `src/events.js`)
동시 진행이 가능하다.

### 5순위 이후 — 사운드, 다국어, 정밀 캘리브레이션
캐주얼 유저 우선순위상 후순위로 둔다. 사운드는 최소 SFX 몇 개면 충분, 다국어는 콘텐츠(2·3순위)가
어느 정도 쌓인 뒤에 하는 게 번역 재작업을 줄인다. 정밀 캘리브레이션(경쟁 AI 초기값, 노드 곡선)은
"재미"에 기여도가 낮다고 판단해 가장 뒤로 뺀다 — 필요하면 언제든 앞당길 수 있음(반론 환영).

## 개발 구조 관점

- 기존 `src/core.js`/`src/ui.js` 분리를 유지하되, 1·2순위 작업을 위해 **`src/events.js`를 신설**
  — 뉴스 이벤트 텍스트 뱅크와 트리거 로직을 `core.js`(순수 시뮬레이션)에도 `ui.js`(렌더링)에도
  안 섞이게 분리. 카피를 만지는 사람이 로직 코드를 건드릴 필요 없게 하는 게 목적.
- `build.js`는 이미 세 파일을 합치는 구조이니 네 번째 소스 파일 추가는 자연스럽게 확장 가능
  (플레이스홀더 하나 추가하는 정도).

## 에셋 관점

- **외부 이미지/오디오 파일 에셋 도입에는 신중론**이다. "단일 HTML 파일" 원칙(핸드오프 문서 명시,
  변경 불가 축)을 지키려면 이미지도 base64 data URI로 인라인해야 하는데, 파일 크기와 유지보수성이
  급격히 나빠진다. 그래서 1~3순위는 의도적으로 **에셋이 필요 없는 항목**만 골랐다. 4순위(비주얼)도
  가능하면 canvas/SVG 절차적 드로잉을 우선하고, 진짜 이미지 파일이 필요해지는 순간은 최대한 늦추자는
  입장. 사운드도 마찬가지로 Web Audio API 절차적 생성이나 아주 짧은 base64 임베딩부터 검토.
- 이 부분은 Codex 안과 가장 갈릴 수 있는 지점이라고 예상한다 — 토론 포인트로 남겨둔다.

## 토론에서 다투고 싶은 지점 (스스로 제기하는 반론 포인트)

- 인과 가시화를 1순위로 두는 게 정말 캐주얼 유저에게 재미로 느껴질지, 아니면 "설명충" UI로
  느껴져 오히려 몰입을 깰지는 확실하지 않다 — Codex가 반대로 "비주얼/서사 먼저, 설명은 나중"을
  주장한다면 타당한 반론이라고 본다.
- 외부 에셋(이미지/사운드 파일) 도입에 대한 신중론이 과도하게 보수적일 수 있다 — 캐주얼 게임
  시장 기준으로는 실제 아트가 없으면 첫인상에서 이탈률이 높을 수 있음.
